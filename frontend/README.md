# TimeTrack Pro V1

Build a time and labour management web app for a company of up to 500 employees, similar to Replicon. ▎ ▎ Users and roles: Employee, Manager, Payroll Admin, System Admin. Sign-in with email and password. Admins create users and assign each employee a manager. ▎ ▎ Time tracking: employees clock in and out (with breaks) from the browser, or fill a weekly timesheet by day. Each time entry is charged to a project and task. Entries can be marked billable or non-billable. ▎ ▎ Projects: admins create clients, projects and tasks, with an hourly bill rate per project. ▎ ▎ Timesheet approval: employees submit their week. The manager approves or rejects it with a comment, and a rejected sheet goes back for editing. Approved sheets are locked. ▎ ▎ Time off: employees request leave (annual, sick, unpaid) for full or half days. The manager approves it. Each employee sees their leave balance, which grows by a fixed number of days per month. ▎ ▎ Labour rules: an admin sets the daily and weekly overtime limits, for example 8 h per day and 40 h per week, plus the minimum break after 6 hours. The app flags overtime and missed breaks on the timesheet and in a compliance report. ▎ ▎ Reports: hours by employee, project and week; billable versus non-billable hours; overtime; leave taken. Export to CSV, including a payroll export of approved hours per employee per period. ▎ ▎ Notifications: in-app alerts for a timesheet due, approved or rejected, and a leave request decided. ▎ ▎ Audit: record who changed or approved any timesheet, and when.

Generated by the Quorq AI SDLC platform from an approved app design.

Every screen here was generated from a design the team reviewed and approved.
A backend was also generated for this project (see `../backend/`), but these
screens still run on **seeded sample data** -- wiring a given screen to a real
endpoint is the next job, not something this repository pretends to have done.

## Approved technology stack

- **Frontend**: React 19
- **Backend**: FastAPI 0.115
- **Database**: PostgreSQL 16
- **Cloud**: AWS

## Running it

```bash
npm install
npm run dev
```

`npm run build` bundles the app; it does not typecheck. The screens were generated, and a
generated screen that renders correctly can still not satisfy `tsc` -- usually an untyped
`useState({})` that is then read for named fields. Deployment would fail on that, which is
a poor reason not to ship a working prototype.

`npm run typecheck` runs `tsc --noEmit` when you want it, and is worth fixing before this
becomes a codebase anyone maintains.

## Checks and tests

- `npm run lint` / `npm run lint:fix` -- ESLint over the whole app; `lint:fix` applies the
  fixes it can. The platform runs `npm run lint` as a gate during development, so keep it green.
- `npm run test` -- Vitest component tests, beside the components they cover.
- `npm run test:e2e` -- Playwright acceptance tests from the `e2e/` folder beside `src/`.
  `npm run test:e2e:install` fetches the browser first. With `E2E_BASE_URL` set it runs against
  that deployed URL; without it, Playwright builds and serves this app and runs against that.

## Layout

- `src/screens/` -- one module per approved screen.
- `src/App.tsx` -- the navigation shell and the route table.
- `src/lib/ui.tsx`, `src/lib/icons.tsx` -- the component and icon vocabulary
  the screens were written against.
- `src/lib/brand.ts`, `src/index.css` -- the approved brand, as tokens and as
  CSS variables.
